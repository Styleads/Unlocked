# Agent 4 — Decisions

`plan.md` §2.6 and the Member 1 section B are the spec; `docs/agents.md` §5 is the team's sketch. Where they differ, `plan.md` wins.

1. **Built in this repo by Member 2** (Varun's call, 2026-10-31), though plan.md assigns Agent 4 to Member 1. Standalone package, no `member2` imports (the demo's `--live` flag is the one exception, and it is a script).
2. **All four plan items** built: email draft, `.ics`, progress tracking, rejection help.
3. **`ActionArtifact` keeps agents.md §5.1 fields** (`action_type`, `title`, `body_content`, `target_destination`, `instructions`, `user_review_confirmed`) and adds `status`, `subject`, `filename`, `mime_type`, `missing_fields`, `source_urls`, `warnings`, `generated_by`. `ActionType` adds `progress_update`.
4. **The LLM only words emails and reads rejection notices.** Python decides what may appear: contacts must be sourced, numbers must be in the sources, quotes must be verbatim.
5. **Email numbers rule:** any number of two or more digits in an LLM draft that isn't in the scheme name, department, question, deadline, facts or allowed URLs rejects the whole draft (template used). Stricter than patching, and an invented date is worse than plain wording.
6. **User detail values never reach the LLM.** They are `{{Key}}` tokens, filled in after validation, so the checks never alter or flag them. Tokens the LLM drops are appended under "My details".
7. **The user's own question is theirs.** Contacts typed in it are kept; it is redacted (Aadhaar-like 12-digit numbers, phones, emails) before reaching an LLM.
8. **agents.md §5.3 `.ics` replaced**: its DTSTAMP was the deadline, it timed deadlines at 09:00 UTC (2:30 PM IST), didn't escape commas/semicolons, used LF and could exceed 75 octets. Ours: all-day deadlines, IST appointments with a VTIMEZONE (no DST in India), real DTSTAMP, uuid5 UID stable per scheme+kind+date.
9. **Calendar never guesses.** No time for an appointment → `needs_input` with `start_time`; default appointment length 1 hour when only a start is given.
10. **Progress is four independent facts**, each with `reported_at` and `simulated`. Follow-ups ask about the earliest implied-but-unknown stage. Contradictions are kept and warned about, never corrected.
11. **Rejection next steps need verbatim evidence** from a provided guidance passage, a valid route (`correction | reapplication | appeal | clarification`), and a description with no unsourced numbers. A reason summary is shown only with a verified reason quote.
12. **Logging:** task name, scheme id and exception type only.
13. **`SchemeContext` uses `from_attributes=True`** so a member2 `SchemeRecord` object (what the backend holds) is accepted, not only its dict. Found when running Agent 4 on live canonical records: all entry points raised `ValidationError`.
14. **`facts_from_scheme(scheme, *, attributes=None, limit=5)`** turns a scheme's rules into email facts: only `verified` rules with both `evidence` and `source_url`, one per distinct quote (compound-rule parts share one), optional attribute filter, capped at 5. Duck-typed, no member2 import. Without it every backend route would rebuild this and could quote unverified text as official.
15. **Clarification questions come from the data, never a fixed default** (`clarification_points` / `clarification_request`). Sources, in order: rules from an official page marked `uncertain` (quoted, one question per quote), official pages that disagree (one verified quote per page), then details the search couldn't find (documents, how to apply, criteria; criteria only if no rule is verified). Unverified rules are never put in a letter. Nothing unclear -> `None`, so the UI offers applying instead. Prompted by the test script's hard-coded "is the income limit per family?" question, which the official text already answered.
16. **Clarification asks only about real ambiguity, one question per topic.** An uncertain rule qualifies only with `uncertain_reason == "group_limits"` or when the source itself marked it uncertain; `not_stated` (our mapping gap, e.g. "B.Sc." vs a coarse course list, "first year") is never put to the department. Quotes on the same topic are merged into one question. Found in the self-test email, which asked about "course type" and "year of study" (twice).
17. **Source-grounded rejection recovery integration (`api/recovery.py`):** `analyse_rejection` outputs feed into controlled action classifications (`correct_document`, `appeal_or_reconsideration`, `alternative_scheme`, `no_supported_remedy_found`). Unmet criteria never trigger automatic appeal recommendations; when no official remedy is verified, alternative schemes from fallback pools are offered instead.
18. **Government-office emails vs Citizen notifications:** Agent 4 email drafts addressed to government departments remain user-reviewed drafts only (`build_email_draft`). The Resend email service (`api/notifications.py`) is strictly for citizen communications (action plans, appointment reminders, deadline alerts), preserving the invariant that Unlocked never sends unsolicited claims to public offices.
19. **Dynamic follow-up link embedding:** Calendar event notes and email bodies incorporate scoped bearer links (`format_follow_up_url`), taking the user straight to the appointment/progress update screen without re-entering demographic details.
20. **Office chat: Python decides, the model only rewords** (review of `feat/whatsappsim`). `decide_chat_turn` is deterministic (status, slot, contact, whether the applicant must approve); a model passed in by the caller may only reword the message, and its text is dropped if it adds a link or a number the original lacked. `agent4` no longer imports `member2`.
21. **Office chat invents nothing.** No default slot/day/time, no default office hours, no default preferences (empty = no constraint), no default phone number. A WhatsApp link is built in Python from a number the simulated office stated. Office data in `fallback_schemes.py` is stripped of invented addresses, numbers and hours and marked `simulated` / `unverified`; a contact with no verification flag is `unverified`.
22. **Applicant decides.** An offered slot is confirmed only by the applicant (or by a pre-authorisation they switched on, and only for a slot inside the days they gave and the published hours). `/advance` waits while a slot awaits approval (409); `/user-input` refuses with nothing to approve; a confirmed appointment is recorded, emailed and put in the appointments table once (IST converted to UTC); `/finish` never relabels a conclusion.

# Member 1 — Potential Issues, Flaws & Code Quality Audit

> **Context:** As of October 31, 2026, Member 1 (M1) delivered the v2 implementation of **Agent 1 (Discovery Agent)**, Kannada translation capabilities, and initial fallback datasets in `feat/agent1v2`.  
> Per team agreement, **Member 2's contracts and data models (`member2/`, `plan.md §5`, `docs/agents.md`) serve as the authoritative standard and priority** for integration.  
> This document logs identified architectural discrepancies, bugs, code quality hazards, and technical debt in Agent 1's deliverables, along with their resolution status and recommended future fixes.

## 1. Critical Bugs & Runtime Hazards

### Issue 1.1: Fictional Gemini Model String (`gemini-3.5-flash-lite`)
* **Locations:**
  - `discovery_agent/agent.py` (Line 55)
  - `discovery_agent/discovery_pipeline.py` (Line 36)
  - `discovery_agent/kannada_translator.py` (Line 429)
  - `live_api_test.py` (Line 11)
  - `test_gemini.py` (Line 19)
* **Severity:** Critical
* **Symptom:** API requests to Google Gemini return HTTP 404 (`Model not found`).
* **Root Cause:** `"gemini-3.5-flash-lite"` is a fictional model name that does not exist in the Google Gemini API catalog.
* **Resolution / Status:** Fixed. Replaced with valid free-tier model `"gemini-flash-lite-latest"` across all references.

### Issue 1.2: Root Interactive Script Blocked Automated Pytest Runs
* **Location:** `test_gemini.py` (Repo root)
* **Severity:** High
* **Symptom:** Executing `pytest` from the repository root causes the test runner to freeze indefinitely.
* **Root Cause:** By naming the file `test_gemini.py` at root, `pytest` auto-discovered it. The script contained an unbounded interactive loop:
  ```python
  while True:
      user_input = input("You: ")
  ```
* **Resolution / Status:** Fixed. Renamed file to `demo_gemini_interactive.py`, preventing test discovery while preserving the interactive manual demo script.

### Issue 1.3: Repository Clutter & Case Collision (`Plan.md` vs `plan.md`)
* **Locations:** `Plan.md`, `Unlocked/`
* **Severity:** Medium
* **Symptom:** File checkout collisions on macOS and Windows file systems (case-insensitive); git submodule warning on `Unlocked/`.
* **Root Cause:** `Plan.md` (2 KB) was committed alongside the master project specification `plan.md` (61 KB). A rogue submodule link was committed as `Unlocked/`.
* **Resolution / Status:** Fixed. Deleted `Plan.md` (master `plan.md` retained) and removed `Unlocked/` submodule gitlink. Root audit documents (`AUDIT_REPORT.md`, `DECISIONS.md`, `HANDOFF_MEMBER3.md`, `PROJECT_LOG.md`) organized into `docs/m1/`.

## 2. Integration & Contract Incompatibilities (Agent 1 $\rightarrow$ Agent 2/3)

### Issue 2.1: Data Schema Divergence from Canonical `member2.models.SchemeRecord`
* **Locations:**
  - `discovery_agent/scheme_schema.py`
  - `discovery_agent/fallback_schemes.py`
  - `discovery_agent/scheme_extractor.py`
* **Severity:** Critical
* **Symptom:** When M1's extracted scheme records are passed directly into Member 2's downstream pipeline:
  1. **Questions:** 0 eligibility questions are generated by `generate_consolidated_questions()`.
  2. **Checklist:** All documents are excluded by `build_action_plan()` with warnings.
  3. **Assessments:** Schemes fail to validate or evaluate.
* **Root Cause:** M1's internal schema diverges across 10 key fields from `plan.md §5.1` and `member2.models.SchemeRecord`:
  | Field in M1 `SchemeRecord` | Field in M2 / Contract | Consequence if Unmapped |
  | :--- | :--- | :--- |
  | `description` (str) | `summary` (str) | Summary disappears in UI and downstream prompts |
  | `target_groups` (list[str]) | `target_group` (list[str]) | Target group criteria cannot be matched |
  | `benefits` (list[str]) | `benefit` (Any / formatted str) | Scheme benefits missing from action plan |
  | `required_documents` (list[str]) | `documents` (list[DocumentRequirement]) | Plain strings lack `source_url` & `evidence`; Agent 3 discards them all |
  | `eligibility_criteria` (list[SchemeCriterion]) | `requirements` (list[Requirement]) | Lacks `operator`, canonical `attribute`, and verification fields; normalizer finds 0 criteria |
  | `official_url` (str) | `official_sources` (list[str]) | Verification pipeline cannot cite official source |
  | `discovery_source` (str) | `source_type` (`"live_search"` \| `"fallback"`) | Source tagging broken |
  | `missing_information` (list[str]) | `uncertainties` (list[str]) | Pipeline uncertainties unrecorded |
  | `verification_status: "partially_verified"` | `"not_verified"` / `"uncertain"` | Pydantic validation failure on `VerificationStatus` |
* **Resolution / Status:** Addressed. Implemented `discovery_agent/adapter.py` providing bidirectional conversion and updated `fallback_schemes.py` to produce canonical `member2.models.SchemeRecord` instances.

### Issue 2.2: Sourceless Plain String Documents in Fallbacks
* **Location:** `discovery_agent/fallback_schemes.py`
* **Severity:** High
* **Symptom:** Fallback schemes defined `required_documents` as flat string lists (e.g. `["Aadhaar card", "Bank account details"]`).
* **Impact:** Member 2's planning engine excludes any document where `doc.source_url is None` (per M2 Issue 3.1). As a result, the action plan checklist was completely empty.
* **Resolution / Status:** Updated fallback schemes so every document requirement is instantiated as a `DocumentRequirement(name=..., source_url=official_url, evidence="Required document")`.

### Issue 2.3: Non-Canonical Attribute Naming & Non-Standard Operators
* **Location:** `discovery_agent/scheme_extractor.py` & `fallback_schemes.py`
* **Severity:** Medium
* **Symptom:** M1 used ad-hoc attribute names (e.g. `occupation`, `land_holding`, `state_resident`) and plain string operators rather than canonical attributes from `member2.attributes` (e.g., `domicile_karnataka`, `annual_family_income`, `is_farmer`) and `Operator` enums (`lte`, `gte`, `eq`, `is_true`).
* **Resolution / Status:** Canonical attribute resolution wired into the compliance adapter using `member2.attributes.resolve_attribute()`.

## 4. Performance & API Quota Limits

### Issue 4.1: Excessive Tavily API Quota Consumption
* **Location:** `discovery_agent/discovery_pipeline.py` (`build_search_queries` & `_run_search`)
* **Severity:** High
* **Symptom:** A single invocation of `discover_schemes` executes 6 search queries in parallel, requesting 10 results each:
  ```python
  # 6 queries * 10 results = 60 search results, burning 6 Tavily credits per call
  search_tasks = [_run_search(q) for q in queries]
  ```
* **Impact:** On the free tier (1,000 monthly credits), fewer than 15-20 discovery sessions will completely deplete the API key.
* **Recommended Fix:**
  1. Reduce default generated queries from 6 to 2–3 high-intent search phrases.
  2. Reduce `limit` per search query from 10 to 4–5.
  3. Introduce caching for identical query strings to avoid repeating identical web searches across test and demo runs.

### Issue 4.2: High Latency and Overhead in Full-Document Kannada Translation
* **Location:** `discovery_agent/kannada_translator.py`
* **Severity:** Low / Performance
* **Symptom:** `kannada_translator.py` is over 640 lines with exhaustive schema prompts and regex validators. When translating live search results on the fly, multiple sequential LLM calls introduce significant user-facing latency.
* **Recommended Fix:**
  - Cache translated fallback records locally (static overlay dictionary).
  - Perform live LLM translations asynchronously only when the user explicitly requests Kannada output (`locale="kn"`).
